    - `MERCHANT_PROBE_V1`

## 3. 数据访问层设计

### 3.1 MySQL 访问函数

- 用户
  - `_get_user_by_phone`
  - `_get_user_by_account`
  - `_get_user_by_uuid`
  - `_create_user_by_phone`
  - `_update_user_password`
- 用户资料
  - `_get_profile_by_user_id`
  - `_merge_profile_to_db`
- 会话审计
  - `_save_auth_session_to_db`
  - `_revoke_auth_session_in_db`
- 密码重置日志
  - `_log_password_reset`

设计要点：

- 密码采用 `pbkdf2_sha256`
- 资料更新为“仅补齐缺失字段 + 可更新称呼偏好”
- `gender` 与 `preferred_name` 均保存在 `profile_json`
- 会话审计按 token 哈希落库

### 3.2 Redis 访问函数

- 鉴权会话：`auth:session:{token}`
- 验证码：`auth:sms:{scene}:{phone}`
- 冷却计时：`auth:sms:cooldown:{scene}:{phone}`
- 密码重置校验态：`auth:pwdreset:verified:{phone}`
- 聊天历史：`RedisChatMessageHistory(session_id=user_uuid)`
- 质量指标：`jiyi:quality:*`
- provider flag：`jiyi:feature_flags:v2`
- provider 探测缓存：按 merchant probe key 缓存额度/会员状态

## 5. 路由与业务设计

### 5.1 页面路由

- `GET /`、`GET /index`：已登录渲染聊天页，否则重定向 `/login`
- `GET /login`、`GET /register`：已登录重定向 `/index`
- `GET /forgot-password`、`GET /reset-password`：忘记密码页

### 5.2 鉴权路由

- `POST /auth/send_code`
  - 校验手机号 + 冷却
  - 生成验证码写 Redis，开发模式可返回 `debug_code`
- `POST /auth/verify`
  - 支持 `mode=login/register`
  - 注册时校验密码规则并建用户
  - 写登录态 Cookie + MySQL 审计
- `POST /auth/login/password`
  - 按账号密码登录
- `POST /auth/password/verify_code`
  - 校验忘记密码验证码并写短期校验态
- `POST /auth/password/reset`
  - 校验通过后更新密码并落审计日志
- `GET /auth/me`
  - 返回当前用户和已存基础资料
- `POST /auth/logout`
  - 清理 Redis 登录态、撤销审计会话、删除 Cookie

### 5.3 聊天路由 `POST /chat`

主链路流程：

1. 鉴权校验
2. 时间锚点构建（`build_time_anchor`）
3. 会话 ID 绑定用户 UUID
4. 资料融合
   - `extract_profile_from_history`
   - `extract_profile_from_query`
   - `merge_session_profile`
5. 问题分类
   - `get_fast_reply`
   - `route_dream_pipeline`
   - `route_zodiac_pipeline`
   - `route_fortune_pipeline`
   - `Master.run`
6. 输出后处理
   - `sanitize_output`
   - `validate_time_consistency`
   - `_enforce_min_answer_contract`
7. 指标上报
   - `track_output_quality`
   - `_log_route_observability`

### 5.4 profile seed 特殊路径

当用户只是在补资料，例如：

- `我叫张三，2001-08-15出生，我是女生`

系统会进入 `profile_seed` 路径，优先返回确定性的记忆确认文案，而不是让大模型自由发挥，避免出现“你小姐”“你叫你”这类不自然表达。

## 6. provider 路由设计

### 6.1 命理资料门禁

当前命理主链路要求以下资料完整：

- `name`
- `birthdate`
- `gender`

`birthtime` 属于增强项，不是硬门槛。缺失时通过 `build_fortune_missing_reply` 给出补资料提示。

### 6.2 星座 / 生肖路由

- 显式星座问法：优先走 `Zhanbu/yunshi`
- 显式生肖问法：优先走 `Zhanbu/yunshi`
- 未显式提供星座/生肖但已有出生日期：自动推断
- 无生日且无星座/生肖时：澄清

### 6.3 fortune 路由

按具体问法选择 provider：

- 今日/明日个人运势：`Bazi/yunshi`
- 今年/明年/某年运势：`Bazi/weilai`
- 通用财运：`Yuce/caiyun`
- 某年财运 / 多年财运对比：`Bazi/caiyunfenxi`
- 姻缘趋势：`Yuce/yinyuan`
- 正缘画像：`Yuce/zhengyuan`
- 结婚预测：`Yuce/jiehun`
- 具体事项择时：`Gongju/zeshi`
- 其他综合命理：`Bazi/cesuan`

### 6.4 provider flag 与回退

当前受控开关：

- `merchant_probe_v1`
- `bazi_daily_v1`
- `bazi_future_v1`
- `wealth_year_v1`
- `zodiac_api_v1`
- `zeshi_api_v1`
- `love_profile_v1`

策略：

1. provider flag 关闭时，直接走旧行为或后备路径
2. provider 调用失败时，必要时触发 `Free/querymerchant` 探测
3. 输出不暴露接口名、内部错误码、原始异常

## 7. 输出与质量治理

### 7.1 输出治理

- 去工具名、去函数名、去原始错误
- 去资料原文污染与生硬回显
- 正缘场景可返回 `extra.partner_portrait_image`
- 星座/生肖回复不展示“参考强度/参考分值”

### 7.2 时间一致性策略

- 对时间敏感问句执行日期/星期一致性校验
- 支持窗口修补与严重冲突回退
- 长周期问法不应被错误收缩成三天窗口

### 7.3 质量指标

`get_quality_metrics(days=days)` 聚合：

- 路由命中：`fortune_route_hit_rate`
- 工具成功：`fortune_tool_success_rate`
- 字段完整度：`fortune_field_completeness_rate`
- 输出质量：`template_repeat_rate`、`template_signature_rate`
- 安全合规：`profile_echo_violation_rate`
- 时间一致性：`temporal_consistency_hit_rate`

## 8. 前端详细设计

### 8.1 登录与注册页

- 文件：`static/js/login_multi.js`、`static/js/auth.js`
- 功能：短信验证码登录、账号密码登录、注册流程
- 交互：发送验证码倒计时、参数前置校验、错误提示

### 8.2 忘记密码页

- 文件：`static/js/reset_password.js`
- 流程：发送验证码 -> 校验验证码 -> 设置新密码

### 8.3 聊天页

- 文件：`static/js/main.js`
- 行为：
  - 初始化拉取 `/auth/me`
  - 发送消息到 `/chat`
  - 打字机渲染、建议按钮、登出
  - 在 `extra.partner_portrait_image` 存在时追加正缘画像卡片

## 9. 异常与返回策略

- 参数错误：`400`
- 未登录：`401`
- 发送过快：`429`
- provider 失败：返回友好文案 + 内部 reason code，不暴露堆栈

## 10. 现阶段边界

- 验证码回传仅适用于开发调试
- 会话历史以 Redis 短期保存为主
- 外部模型与 provider 依赖波动会影响回答质量上限
